# Product Contract Matrix

> **Status:** Working audit artifact. Evidence-backed against the tree on branch `claude/rust-arch-audit-gaps-immuk1` (2026-07-04). Every "Current Evidence" cell cites `file:line` from the code as it stands. This document deliberately separates *code-artifact maturity* (is the Rust real, tested, deterministic?) from *product-capability maturity* (does the shipped binary do the thing the README promises to a user?). The two diverge sharply, and that divergence is the subject of this file.

## Guiding question: what must this system really be able to do to be more than a research simulation?

The repository markets itself as a **"Production-oriented, pure Rust runtime"** (`README.md:3`) offering **"policy-driven, cryptographically-audited traffic routing without third-party proxy software"** (`README.md:39`) — an in-process **Proxifier replacement** (`docs/NETADMIN_SPEC.md:5-8`) with DNS protection, a kill-switch, and a desktop dashboard.

To be that product — and not a well-engineered decision/audit *simulation* of that product — the system must cross one specific boundary that it has not yet crossed: **a real byte must leave the process under policy control, and the user must be able to see truthfully whether it was protected.** Concretely, "more than a research simulation" requires all of the following to be simultaneously true:

1. A user names a real destination and the tool routes (or refuses to route) real traffic through a real adapter — TCP/SOCKS5/HTTP-CONNECT/TLS/DNS.
2. The daemon's `Protected`/`dns_protected`/`kill_switch` status reflects a real transport state, not a hardcoded constant.
3. A rejection or degradation actually stops traffic (fail-closed with teeth), not merely records a `Deny` decision about traffic that was never intercepted.
4. Dissolution/TTL sweeps, audit records, and residues that the docs call "operational" actually run in a product path and are durably persisted and observable.
5. The advertised guarantees that CI claims to verify (e.g. `no_std`) actually hold in-tree.

Today, **none of (1)–(4) holds**, and **(5) is broken in-tree**. What *does* exist is a genuinely real, deterministic, well-tested **decision/audit/planning core** plus a **local Unix-socket daemon skeleton** — a level-4 code artifact. The gap between that and the product contract is not "polish"; it is the entire live data plane (`ssk-netcore`, Phase 3) and traffic ingress (`ssk-capture`, Phase 4), **neither of which exists as a crate in the workspace** (confirmed absent: `crates/ssk-netcore`, `crates/ssk-capture`).

The honesty of the codebase is itself split: the **live daemon status is candid** (`dns_protected=false`, empty flow list, `"unknown (ssk-netcore not yet integrated)"`), and `docs/DESKTOP_CLIENT_ARCHITECTURE.md` is an internal audit that already contradicts the marketing layer (its Section B.6 is titled *"Doc-vs-code discrepancies to correct"*). The overclaims live in `README.md`, `docs/NETADMIN_SPEC.md`, and `docs/COMPLETION_CHECKLIST.md`, not in the running code.

## Two hard falsifiers of "done"

Two items are not opinion-based maturity judgments but concrete, reproducible counterexamples to any "green means shippable" reading.

1. **The advertised `no_std` guarantee fails in-tree.** `README.md:102,342-343,371` claim `ssk-core` is `no_std`-friendly and "verified in CI via `cargo check --no-default-features`" (the `no_std_core` job, `.github/workflows/ci.yml:75-81`). The command as written fails: `cargo check -p ssk-core --no-default-features` → exit 101, `E0433`/`E0425` "cannot find type `Vec`" at `crates/ssk-core/src/connection.rs:55`, `:78`, `:87` (bare `Vec`, no `use alloc::vec::Vec`). A documented, CI-claimed capability is broken. **Minimal fix:** add `extern crate alloc; use alloc::vec::Vec;` to `connection.rs`.

2. **The product's headline capability has no code and no test.** No socket is opened, no DNS resolved, no packet routed anywhere in the workspace; the responsible crate `ssk-netcore` (and ingress `ssk-capture`) do not exist. Every "protection" test reaches `Protected` through `AlwaysUpMockDataPlane` (`crates/ssk-daemon/src/mock_dataplane.rs:17-21`, wired at `main.rs:53`).

## Bottom line

As a **code artifact**, this is a real, tested, deterministic decision/audit/planning core plus a real local IPC daemon skeleton — level 4, and honestly built. As the **network/privacy product** the marketing layer describes, the load-bearing layer is not present: no real egress, no traffic capture, config parsed and dropped, dissolution sweeps and audit records that never run in a product path, and a release that ships source rather than a runnable binary. Closing the gap is not incremental hardening of the existing crates; it is the construction and integration of the absent `ssk-netcore` (Phase 3) and `ssk-capture` (Phase 4) layers, followed by the first end-to-end test in the tree that asserts a real network effect. Until that test exists and is green, the accurate claim is: **a faithful decision/audit simulation of the product, not the product.**
